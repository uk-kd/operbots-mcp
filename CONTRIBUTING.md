# Разработка

```bash
npm install && npm run build
claude mcp add operbots-dev -- node ./dist/index.js
```

Требуется Node 20 или новее. `npm run typecheck` — проверка типов без сборки,
`npm test` — сборка, native `node:test`, HTTP/SDK stdio и проверки обоих плагинов;
`npm run watch` — пересборка на лету. Обычные тесты используют временные профили
и локальные тестовые HTTP-серверы, к рабочей панели не обращаются.

Что где лежит:

```
src/index.ts      разбор команды: сервер MCP или действие в терминале
src/server.ts     сборка сервера и регистрация инструментов
src/auth.ts       проверка интеграционного токена и текущего пользователя
src/credentials.ts хранилище доступа и блокировка файла
src/context.ts    разбор дел и ботов по имени, короткий кэш
src/tools/        инструменты по разделам панели
scripts/          разнос версии и сборка плагина
plugins/          плагины Codex и Claude Code с собранным сервером
```

`npm run build` собирает дважды: `tsc` даёт обычный `dist/` для пакета npm, а
`scripts/pack-plugin.mjs` сворачивает всё в один файл
`plugins/operbots-mcp/dist/index.js` с вшитыми зависимостями. Этот файл **едет в
репозиторий**, и это осознанно: Claude Code берёт плагин прямо отсюда, а `npx` из
запуска убран — на нём установка и ломалась. Править там нечего, он собирается из `src/`.

Инструмент объявляется данными, а не обращениями к SDK: имя, описание, схема
входа, признак `read | write | danger` и обработчик. Признак уходит в подсказки
MCP — клиент спрашивает разрешение на `danger` — и им же отбирается набор для
режима «только чтение». Отдельная пометка `session` оставляет в этом режиме вход
и выход: они правят не панель, а токен на этой машине, а без них человек с
отозванным токеном получал бы в каждом отказе совет вызвать `operbots_login` —
инструмент, которого у него нет. Новый инструмент достаточно добавить в массив
своего раздела и подключить раздел в `src/server.ts`.

Описания инструментов и текст ошибок читает модель: они на русском и объясняют
не только что делает вызов, но и чем это обернётся — что заменяется целиком,
что необратимо, что расходует чужие лимиты.

# Выпуск

Одна команда:

```bash
git tag v0.1.2 && git push origin v0.1.2
```

Метка запускает `.github/workflows/release.yml`: номер берётся **из неё** и
разносится по `package.json` и плагину, проходит проверка типов и запуск
собранного сервера со сверкой версии, пакет уходит в npm с отметкой о
происхождении, появляется релиз GitHub с архивом и заметками, а версия
возвращается коммитом в `main` — иначе плагин Claude Code показывал бы номер
прошлого выпуска.

Номер в `package.json` править руками не нужно: источник правды — метка.
Повторный запуск по той же метке не падает: опубликованная версия пропускается,
существующий релиз получает свежий архив.

Секретов не требуется. Право публиковать выдаётся по OIDC через «Trusted
Publisher» на странице пакета в npm; доверие привязано к этому репозиторию и к
файлу `release.yml` — переименуете файл, поправьте привязку, иначе публикация
откажет. Действию нужны права `contents: write` и `id-token: write`, а в
настройках репозитория — Actions → General → Workflow permissions → Read and
write.

Каталог плагина (`.claude-plugin/marketplace.json`, `plugins/operbots-mcp/`)
живёт здесь же и отдельной публикации не требует: Claude Code берёт его прямо
из репозитория.

## Проверка плагинов Codex и Claude Code

`node scripts/plugin-smoke.mjs` проверяет согласованность версий и запускает
упакованный сервер по конфигурации каждого клиента из посторонней папки с пробелами.
Проверяются рукопожатие MCP, список 143 инструментов и режим чтения (56 инструментов).
Тест использует пустой временный профиль и не обращается к рабочей панели.

При выпуске `sync-version.mjs` обновляет все три манифеста. Переносимые
`plugins/operbots-mcp/plugin.json` и `mcp.json` нужны Codex; манифест
`.claude-plugin/plugin.json` сохраняет подключение Claude Code.

## Проверка настоящего backend

`tests/backend-fixture.py` запускается из окружения Python sibling-репозитория
`operbots/backend` после миграций отдельной базы `operbots_mcp_qa` на `127.0.0.1`.
Нужны переменные `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_USER`,
`POSTGRES_PASSWORD`, `POSTGRES_DB=operbots_mcp_qa`, отдельный `SECRET_KEY`,
`DB_POOLED=false`, `OPERBOTS_QA_DISABLE_REDIS=1` и `OPERBOTS_QA_FIXTURE` — путь
к новому временно́му JSON-файлу. Fixture отключает Redis и lifespan приложения,
поэтому боты и постоянные фоновые планировщики не запускаются. Отдельные операции
могут запускать свою обработку; у тестовой базы знаний нет ИИ-провайдера.

После появления файла выполните в MCP-репозитории `npm run test:backend` с тем
же `OPERBOTS_QA_FIXTURE`. Проверяются реальные права владельца/наблюдателя,
изоляция дел, revisions, связанные ресурсы, история и настройки через SDK stdio,
HTTP и PostgreSQL. Также проверяются скрытые ссылки приглашений, запрет расширения
чужих прав, активация сценариев по виду и правам, восстановление архивного бота
и смена пароля через API-ключ. Для восстановления подменяется только проверка
токена платформой; запросы к Telegram не выполняются.
Скрипт удаляет fixture-файл, останавливая тестовый сервер.
Базу и контейнер создавайте отдельно от рабочей установки и удаляйте после проверки.
В fixture-файле находятся только временные тестовые токены; не печатайте его.
