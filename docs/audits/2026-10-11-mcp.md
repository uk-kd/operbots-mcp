## Исправить в первую очередь

### 1. P1 — invite_id позволяет изменить адресуемый ресурс

**Что проверено.** [invites_revoke](../../src/tools/people.ts#L467) принимает invite_id через z.string() и вставляет его непосредственно в URL DELETE.

**Проблема.** Схема принимает несколько сегментов пути. Изолированный probe вызвал настоящий обработчик с mock API и подтвердил, что нормализация принятого значения может превратить путь invitations в путь bots того же дела; настоящее удаление не выполнялось. Таким образом, назначение инструмента и клиентские проверки подтверждения другой операции не ограничивают его HTTP-цель.

**Минимальное исправление.** Заменить проверку invite_id на UUID, как у остальных адресуемых ресурсов, и добавить отрицательный тест недопустимых сегментов. Серверную проверку прав сохранять независимо от этой схемы.

**Если оставить.** Ошибочный аргумент модели может направить удаление не на тот вид объекта. Запрос всё ещё выполняется с правами текущего пользователя: обход серверных прав или повышение привилегий не утверждается.

### 2. P1 — неоднозначное имя сценария молча выбирает первый

**Что проверено.** [locate](../../src/tools/flows.ts#L373) сначала ищет UUID, затем первое точное и первое частичное совпадение имени через find. Используется для чтения, сохранения, публикации, копирования, экспорта и удаления.

**Проблема.** Два сценария «Поддержка» или «Поддержка сайта»/«Поддержка магазина» принимают общий hint «Поддержка» и выбирают первый. Probe использовал настоящий flows_get с локальной подменой списка; в [Context.pickByName](../../src/context.ts) уже существует правильный отказ при неоднозначности для других сущностей.

**Минимальное исправление.** Сохранить точный выбор по UUID, а имена передавать существующему pickByName. При неоднозначности вернуть список UUID, не выполнять следующую операцию.

**Если оставить.** Даже владелец одного дела с несколькими сценариями может изменить или включить другой сценарий.

### 3. P1, общий backend — успешный ответ приходит раньше commit

**Что проверено.** [scripts/backend-smoke.mjs](../../scripts/backend-smoke.mjs#L85) вызвал flows_save(copy_of, name, description:null) на реальном локальном backend с PostgreSQL, owner/viewer/read-only MCP-подключениями.

**Проблема.** Внутреннее создание копии вернуло успех, последующий PUT той же копии — «Сценарий не найден». После завершения запроса SQL показал QA copy: операция создания была выполнена. Корень в operbots/backend/app/api/deps.py:44 и core/database.py:81 — commit происходит после HTTP-ответа.

**Минимальное исправление.** Исправить жизненный цикл HTTP-транзакции backend до отправки 2xx. Затем заново выполнить штатный smoke на свежей одноразовой базе; не подставлять бесконтрольный retry или задержку в рабочий MCP.

**Если оставить.** Составные инструменты и немедленное перечитывание периодически возвращают ошибку уже после частично выполненной операции; повтор пользователем может создать лишнюю копию.

Диагностический повтор с ожиданием 250 мс после ответов изменяющих HTTP-операций дошёл дальше, но затем получил устаревший список ботов после bots_detach. Поздний SQL подтвердил archived_at. Этот запуск также не считается пройденным: фиксированная задержка не гарантирует завершение транзакции. Диагностический [fetch-settle.mjs](2026-10-11-fetch-settle.mjs) требует явный флаг и проверяет fixture.database/127.0.0.1; это только лабораторный preload.

### 4. P2, общий контракт — граф не защищён от устаревшего сохранения

**Что проверено.** flows_save читает текущий Flow и отправляет PUT без ожидаемой версии; backend FlowUpdate такой версии не требует. Проверка двух редакторов проведена отдельно на одноразовой PostgreSQL.

**Проблема.** Прочитанный ранее граф перезаписывает более новую правку и принимается как следующая корректная version. В requests/types явные revision/version уже реализованы и не заменяются автоматически при конфликте.

**Минимальное исправление.** Добавить expected version в backend-контракт и flows_save, сохранив её от чтения до записи. При 409 вернуть конфликт пользователю и перечитать граф для явного объединения.

**Если оставить.** MCP и вкладка панели могут незаметно отменить работу друг друга.

### 5. P2, общий контракт — null не очищает описание сценария

**Что проверено.** Схема flows_save принимает nullable description и передаёт его через body. Настоящий QA PUT с description:null после зафиксированного непустого значения возвращает 200, сохраняя старое описание.

**Проблема.** Backend FlowService.update проверяет description is not None вместо присутствия поля в payload. Ошибка находится на сервере; nullable-схема MCP её не исправляет.

**Минимальное исправление.** На backend различать отсутствующее поле и явный null через model_fields_set. Добавить сквозной контрактный тест set → clear → GET, дождавшись правильного commit по №3.

**Если оставить.** Инструмент сообщает успешное сохранение, но описание остаётся прежним.

## Что уже работает и имеет проверки

- SDK/stdio и упаковка плагина для Codex/Claude Code; discovery в обычном и read-only режимах.
- Неоднозначность дела, бота, провайдера, роли, участника и базы знаний обычно корректно отклоняется. Дефект сценариев выделен отдельно.
- UUID/revision/version для заявок, задач и типов, явные false/zero/null, структурированная аудитория рассылки, ошибки прав и конфликтов.
- Перенос графа сохраняет comments, viewport, node data/width и edge data; маскированные секреты не принимаются как новые значения.
- Токен проверяется перед применением; секреты не запрашиваются через MCP-формы. whoami проверяет действительную текущую личность.
- Локальные абсолютные пути, отказ UNC/device paths, upload до 20 МиБ с повторной проверкой фактических bytes, multipart с типом файла.
- Download создаёт новый файл с wx и не перезаписывает существующий; redirects отклоняются, ответы и ошибки читаются под таймаутом.
- Данные API остаются ограничены серверными правами. Метки danger/annotations помогают клиенту, но сами по себе не являются серверным контролем доступа.

## ООП и оптимизация

Разделение AuthManager → OperbotsApi → Context → инструменты соответствует обязанностям. HTTP-разбор общий для входа и обычных запросов. Введение нового слоя или фабрики для исправления найденных проблем не требуется.

Приоритетная повторная утилизация — общий pickByName и UUID-схемы: дублирование выбора сценария уже привело к отличающемуся поведению. Кэш дела/ботов на 30 секунд разумен для личной панели; инвалидации при изменении учётной записи и ресурсов проверяются тестами.

parseBytes/download читают ответ целиком в память. Для больших выгрузок следует перейти на потоковую запись в новый файл и явный предел размера, сохранив ошибки, таймаут и защиту от перезаписи. При обычном небольшом объёме это рекомендация; потребление памяти на больших файлах не измерялось.

Подтверждённых лишних зависимостей нет: SDK и Zod используются в протоколе и проверке схем. Механическое разбиение больших файлов tools не исправит выбор цели или контракт сохранения.

50 инструментов без прямого упоминания в адресных тестах перечислены в inventory.json. Сначала нужны тесты неоднозначного flow hint и invite_id; затем сквозные операции после создания/копирования, явное очищение nullable полей и совместное редактирование графа с панелью.

## Воспроизведение

Из корня operbots-mcp:

    npm test
    npm run typecheck
    node docs/audits/2026-10-11-probes.mjs

Последняя команда использует mock API, не ходит к реальному backend и не удаляет файлы или объекты. Assertions подтверждают текущие ошибки; после исправления они должны перестать проходить.

Штатный backend-smoke требует tests/backend-fixture.py, свежую мигрированную базу operbots_mcp_qa на 127.0.0.1:15432 и явные QA-переменные. Fixture проверяет имя базы, локальный host и OPERBOTS_QA_DISABLE_REDIS=1, отключает lifespan/ботов/планировщик и подменяет только Telegram inspect. OPERBOTS_QA_FIXTURE указывает временный файл; он удаляется smoke, что останавливает fixture-сервер. Повтор на той же заполненной базе потребует очистки именно одноразовой QA-базы из-за фиксированных адресов fixture-пользователей.

    npm run test:backend

## Итог и ограничения

Сначала исправить два дефекта выбора цели MCP и порядок commit backend. Затем закрыть версию графа и семантику очищения description в общем API, frontend и MCP.

Реальные отправки сообщений/рассылок, рабочие токены, платные AI-запросы и внешние провайдеры не проверялись. Штатная backend-интеграция сейчас не пройдена; успешные 121+5 тестов не снимают перечисленные риски. Прикладные исправления в этой ветке отсутствуют.
